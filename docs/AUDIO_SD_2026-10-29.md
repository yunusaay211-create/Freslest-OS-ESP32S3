# SD sounds and OS audio recovery

The installer welcome page now offers **SD karta ses yükle / Install SD sounds**. Connect the DFPlayer card with a PC card reader and select its drive root. No COM connection is used. The card must already use FAT/FAT32; the installer does not format it. Only numbered MP3/0001.mp3 through 0112.mp3 can be replaced; unrelated files remain. All sources and copied files are checked with SHA-256. Each changed file is flushed and verified before atomic replacement. A failed operation leaves the previous version of that file intact; retry verifies files already completed.

Tracks 0001–0104 match the user's existing DFPlayer music pack. Tracks 0105–0112 are the project's eight original procedural OS cues. The numbered sound pack is included in `audio-payload/*.part`; `python prepare_audio.py` restores it for a fresh checkout. `build_windows.py` also prepares it, and both Windows workflows prepare it before running tests. To regenerate the pack from local MP3 assets, use `tools/prepare_sd_audio.py` and regenerate the payload parts and their manifest.

## Reproduced audio defects

- The previous implementation queried SD file count with 0x47, which DFRobot's library uses for USB. SD uses 0x48; producer, reply parsing and tests now agree.
- If the one-shot insertion notification was lost, the manager could wait forever after a removal. While waiting, an RX-connected module is queried every two seconds; a positive SD count starts source/DAC/volume recovery.
- A long burst of volume changes filled the command ring and could leave stale zero volume. Volume changes are now coalesced, and transmitted volume commands always use current settings.
- Changes between the initialization volume command and ready state were dropped. Pending volume now survives that interval.
- A reported sleeping error previously only appeared in logs. Bounded wake/source/DAC/current-volume recovery now handles it without replaying stale cues. Module silence never triggers repeated resets. When RX replies are available, idle health queries can detect a changed module volume.

## VGA status

VGA remains 640×480, target PCLK 25,175,000 Hz, 800×525 total timing (~59.94 Hz). The OS VGA menu canvas remains 480×320. No palette gains, pin order or resolution changes were made.

The supplied C4 raw-color photo bypasses PLAYPAL and still shows incorrect intensity ramps. This does not establish an electrical cause, and the Doom red tint is **not confirmed fixed**. Code inspection and regression tests found no demonstrated RGB332 conversion or current GPIO-assignment fault. Both OS and Doom now print actual GPIO matrix routes, inversion flags and LCD register state during the raw-color test. Doom's private backend calls this diagnostic from the test so the function remains in the compiled firmware. Hold OK during VGA startup to show the C4 test; capture its serial `VGA ROUTE` / `VGA REG` output for the next physical check. BACK exits the test.

## Validation

- Seven production audio-manager scenarios pass with ASAN/UBSAN, including lost insertion, latest volume, initialization unmute, sleeping error, unexpected module volume and silent RX.
- Full installer/firmware regression suite: 79 tests, one Windows-only boundary test skipped on Linux. All passed. Preserved Viewer: nine tests passed.
- All three OS/Doom display-profile pairs were built from source with ESP-IDF 5.4.4. Partition sizes and payload hashes were checked. All six application images contain the GPIO diagnostic. The legacy root Doom payload and common data payloads are preserved; selected display profiles use the rebuilt applications.
- Windows installer was repacked using Python 3.11 with the original Windows x64 runtime/bootloader. All 1,240 archive entries, 112 audio files, firmware hashes and unchanged entry bytes were verified.
- Native Windows execution and physical ESP32-S3/DFPlayer/VGA tests have not been performed here. The Wine launch check is blocked by this environment denying the wineserver Unix socket; this is not a firmware test result. CI includes native Windows launch and frozen diagnostics checks.

## Windows extraction correction

The first Audio-SD EXE used forward slashes in newly added audio archive entries. Windows bootloader parent-directory creation expects backslashes, so startup failed before Python with `Failed to extract audio_pack/MP3/0001.mp3`. The replacement Audio-SD-Fix EXE uses Windows paths for all 113 audio-pack entries. All 1,229 extracted file paths and all 112 sound contents were verified. `tools/check_windows_archive.py` now checks built Windows executables before release; four regression cases cover the reported path, valid nested paths, unsafe targets and incomplete sound packs. Firmware contents and display settings are unchanged by this packaging correction. The audio payload was split into smaller parts for authenticated source upload; its reconstructed archive bytes remain identical.
