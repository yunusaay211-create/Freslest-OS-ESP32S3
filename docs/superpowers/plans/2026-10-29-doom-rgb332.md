# Doom native RGB332 implementation plan

> **For agentic workers:** Use superpowers:executing-plans for inline execution. Steps use checkbox tracking.

**Goal:** A Doom-owned RGB332 palette/converter and deterministic pixel-word DMA transport, plus a mandatory idle yield during busy demos.
**Architecture:** Keep existing eight physical data GPIOs and double-buffer callback ownership. Use 16-bit peripheral/DMA entries with RGB332 in the low byte and zero upper byte. OS code and menu dimensions remain unchanged.
**Tech Stack:** C, ESP-IDF5.4.4, existing native ASAN/UBSAN regression harness.
**Spec:** docs/superpowers/specs/2026-10-29-doom-rgb332-design.md

## Global constraints
- VGA640×480; target25,175,000Hz; horizontal800 and vertical525 total.
- OS VGA canvas480×320 and current RGB GPIO mapping unchanged.
- No palette gain compensation, blind periodic reset or watchdog disabling.

## Review focus
- DMA word width and output pin width must not accidentally configure GPIO0 for unused lines.
- Buffer allocation, zeroing, color tests and generic progress views must all use the same stride.
- Palette/cursor changes and DMA drops must not suppress a needed frame.
- Slow demo frames must leave idle-task time at every presentation.
- No claim of physical color or reset resolution without device evidence.
