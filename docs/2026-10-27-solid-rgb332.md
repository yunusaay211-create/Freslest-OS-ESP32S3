# Solid RGB332 follow-up

Physical feedback: last installer was flashed, Doom still has intense red/dotted appearance; LCD Doom is normal, OS VGA is also reported abnormal. User confirms eight resistor-DAC color GPIOs; LCD RESET is tied to board reset rather than GPIO8. GPIO41 remains connected to LCD backlight. User requests a code correction rather than another wiring step.

A concrete software defect is reproduced separately from the still-unproven physical red-tint cause: a uniform source palette color does not remain uniform after the added 4x4 ordered pattern. This creates colored dots that do not exist in the source. The previous gray-average test rewarded this behavior and did not test source uniformity.

Both indexed converters now use exactly the supplied working V1.0 core packing: `(r & 0xe0) | ((g & 0xe0) >> 3) | (b >> 6)`. One color index maps to one RGB332 byte at every coordinate. RGB565 OS conversion already matched that core and is unchanged. No speculative channel swap/gain/timing change is applied. Raw Doom PLAYPAL, real damage palettes, double-frame ownership, bounce/XIP, TV fit and LCD menu behavior are preserved. Startup prints FRESLEST_VGA:SOLID332_C3 so the built path can be identified.

Regression: five literal gray/code pairs (32/0x24,64/0x49,128/0x92,192/0xdb,255/0xff) must stay flat over an8x8 region in generic and dedicated Doom outputs, plus existing red/green/blue/white and palette-change tests. The uniform-source assertion failed before the change and passes afterward. This verifies removal of generated dot patterns; physical red tint is not claimed fixed without a new device observation.
